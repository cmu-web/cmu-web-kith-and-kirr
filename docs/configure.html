A Serving Suggestion

The way we'd run Grouper with this theme: single sign-on in front, people from the directory and as few privileges handed out by default as Grouper allows. The theme works the same either way; see Install for the theme itself.

  • Single sign-on is the only way in. A web server in front of Grouper signs people in through Entra or Shibboleth and passes their Andrew ID to Grouper, so nobody keeps a password for Grouper.
  • People come from the directory. Grouper looks people up in the campus directory, so nobody adds a person by hand.
  • New groups are private. A new group grants nothing to everyone; its folder decides who sees it.
  • Few administrators, more viewers. A small group runs Grouper, and a separate group can see everything without changing anything.
  • Only the parts you use. The UI and the daemon run; the web services run only for apps that call them.

Sign In Through Entra or Shibboleth

Put a web server with HTTPS in front of Grouper and have it sign people in: a Shibboleth service provider, or an OpenID Connect module or proxy registered with Entra. Once someone is signed in, the web server sends their Andrew ID to Grouper in a header, and Grouper takes it as the signed-in user. In grouper.properties: 

grouper.ui.authentication.http.header = X-Remote-User

Grouper trusts that header completely, so two things go with it. The web server sets the header on every request, replacing any the browser sent, and Grouper's own port listens only on 127.0.0.1 or a private network, where nothing but the web server reaches it.

People From the Directory

Add a subject source in subject.properties for the campus directory, with the Andrew ID as the identifier the header carries, and names and email from the directory. Grouper then finds people as they're added to groups, and the header's ID matches the person Grouper finds.

Who Gets Which Privileges

Grouper's defaults let everyone read and view each new group. Turn that off in grouper.properties, and grant read and view on folders instead, to the people who work with what's in them: 

groups.create.grant.all.read = false
groups.create.grant.all.view = false

Name a group of administrators, who can do anything in Grouper, and keep it to the few people who run it. Name a group of viewers as well, for a help desk or an auditor: its members see every folder and group and every group's members, and change nothing. 

groups.wheel.group = app:grouper:admin
groups.wheel.viewonly.group = app:grouper:viewer
groups.wheel.readonly.group = app:grouper:viewer

Everyone else gets privileges where they work: an app's owners administer its folder, and the people who keep a group current update it.

What Runs

In Internet2's container, each part of Grouper is a command: ui, daemon and ws. Run the UI and the daemon, which keeps composite groups, loaders and provisioning current. Run the web services only when an app calls them, behind their own sign-in, and leave them off otherwise.
